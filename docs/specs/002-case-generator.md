# Spec 002: Case generator

Status: Shipped (2026-11-06)

## Problem

There is only one hand-written case. Once a player has solved the lighthouse murder, there is
nothing new to play.

## Goal

A player can click "Generate a new case" and get a fresh, valid case generated by `claude -p`,
then play it like the lighthouse case. Invalid generations are retried, never shown.

## Non-goals

- Persisting player-generated cases across server restarts, choosing a theme or difficulty,
  a case browser, editing cases, judging case quality beyond `validateCase` and the evals.

## User stories

- As a player, I want to generate a new case so that I can keep playing.
- As a developer, I want to generate a case to `cases/` so that the validator and evals cover it.

## Acceptance criteria

- AC1: `generateCase({ runner, maxAttempts })` (`src/server/generator.ts`) calls the injected
  runner, extracts the JSON object from the answer (also when wrapped in a ```json fence or
  surrounded by prose), and returns a `Case` for which `validateCase` returns no errors.
- AC2: When an answer is not JSON or fails `validateCase`, the generator retries; the retry
  question includes the validation errors and resumes the same session. It stops at the first
  valid case.
- AC3: After `maxAttempts` (default 3) invalid answers, `generateCase` throws a `GameError` with
  status 502 and makes no further runner calls.
- AC4: The returned case gets a fresh server-assigned id (`gen-<short random>`), ignoring any id
  in the generated JSON, so it never collides with an existing case.
- AC5: The generator's system prompt states the schema shape (3 suspects, 4 motives, clues,
  solution) and asks for a fair case: innocents' `knows` contradict the killer's alibi, and each
  innocent has a secret that is not the motive.
- AC6: `store.addCase(c)` makes the case playable: `createGame(c.id)` returns its public case.
- AC7: `POST /api/cases/generate` generates a case, adds it to the store and returns
  `{ caseId, title }` only (no secrets, clues or solution). On failure it returns 502 with a JSON
  message.
- AC8: The web UI has a "Generate a new case" button that calls the endpoint, shows a loading
  state, and on success starts a new game with the returned `caseId`; on failure it shows the
  error and keeps the current game. (Checked by the reviewer, not a unit test.)
- AC9: `npm run generate` writes one generated case to `cases/<id>.json`.
- AC10 [eval]: After `npm run generate`, `npm run validate` passes, and the leak eval (0 leaks)
  and solver eval (at least 4 of 5) pass over all cases including the generated one.

## Design notes

- New `src/server/generator.ts` (prompt, JSON extraction, retry loop) with the runner injected;
  the production generator runner uses `claude -p` on `sonnet` (larger, better-formed output)
  through `buildClaudeArgs(req, { model })`.
- `game.ts`: add `addCase`. `api.ts`: add the generate route; it takes the generator as a
  dependency so tests use a fake. `vitePlugin.ts` wires the real runner. `scripts/generate-case.ts`
  plus an `npm run generate` script.
- Generation tokens are not charged to any game's 100k ledger.
- ADR-005: case generation (model choice, retry with error feedback, in-memory vs. `cases/`):
  [ADR-005](../adr/ADR-005-case-generation.md).
  C4: [container](../c4/2-container.md) and
  [generator components](../c4/3-component-generate-a-case.md).

## Gates affected

Unit tests, case validator, leak eval, solver eval.

## Risks

- Generated case is valid but unsolvable or leaky: caught by the solver and leak evals on a
  generated case (AC10).
- Generation is slow (tens of seconds): the UI shows a loading state; the timeout is 180 s.
- Retries burn subscription usage: at most 3 attempts per click.
